# LGD-Gate 开源方法论 — 详细手册

## 从 SkillGate 项目沉淀出来的完整开源开发流程

---

## 一、为什么需要这套方法论？

做开源工具最容易踩的坑：
1. **闷头做**——不调研竞品，做了一半发现别人已经做过了
2. **一步到位**——想做一个完美的东西，结果做不出来
3. **测试不足**——只做单元测试，上线后发现一堆问题
4. **没有门禁**——"差不多就行"，结果质量不稳定

LGD-Gate 方法论就是解决这些坑的。

---

## 二、核心三律（LGD）

### 有籍（Registered）
**每个任务有档案可追溯。**

怎么做：
- 维护一个完整的 CHANGELOG，从 v1 到最新版
- 每个版本写清楚：加了什么、改了什么、修了什么
- 每个决策有记录：为什么这么做，不那么做

例子（SkillGate）：
```
v7.3.0 — Coverage Tests Added
  - 加了 test_coverage.py
  - CI 从 14 步涨到 15 步
  - 测试用例从 39 涨到 66
```

### 有证（Evidenced）
**每个结论有出处有证据。**

怎么做：
- 每个功能有测试覆盖
- 每个指标有实跑数据
- 每个说法有来源引用

例子（SkillGate）：
- ❌ 错误："我们的扫描器很准"
- ✅ 正确："F1=100%（小测试集 14 个用例实跑结果）"

### 有门禁（Gated）
**关键节点有检查有验证。**

怎么做：
- CI 全绿才能过
- 误报率/召回率达标才能发
- 红队测试通过才能上线

例子（SkillGate）：
```
CI 15 步全绿：
  ✅ Environment Check
  ✅ Lint Check
  ✅ Unit Tests
  ✅ ...
  ✅ Pressure Test
```

## 三、完整五步法

### 第一步：Trending-to-Gap 调研法

**目标：找到空位，别闷头做。**

步骤：
1. 看 GitHub Trending，收集相关竞品（至少 5-10 个）
2. 拆解每个竞品：
   - 做什么？
   - 不做什么？
   - 优点是什么？
   - 缺点是什么？
3. 找到空位：
   - 没人做的？
   - 做得不够好的？
   - 串不起来的？
4. 定位机会：现有玩家各做一段，没人串成端到端

例子（SkillGate）：
- 竞品：SkillSpector（NVIDIA）只做安全扫描
- 竞品：skillsregistry.net 只做搜索
- 空位：没人做"安全扫描 + 能力评测 + 持续监控 + Trust Score"端到端流水线

### 第二步：Inch-by-Inch 迭代法

**目标：别想一步到位，小步快跑。**

版本节奏：
- v1.0：最小可用版——先做一个能跑的
- v2-v3：加功能——加规则、加语言、加格式
- v4-v5：加评测——加 benchmark、加红队测试
- v6-v7：优化质量——降误报率、加覆盖率、做 E2E

关键原则：
- 每个版本都能跑
- 每个版本都有测试
- 每个版本都比上一个好

### 第三步：Layered-Testing 七层测试法

**目标：别只做单元测试，要七层都测到。**

七层测试：
1. **单元测试**——规则数量、版本号、格式输出
2. **集成测试**——端到端扫描
3. **错误处理**——空文件/二进制/超长行
4. **红队测试**——路径遍历/恶意输入/正则 DoS
5. **严格基准**——精确率/召回率/F1
6. **E2E 模拟**——完整用户流程（扫描→修复→再扫描）
7. **压力测试**——10000 文件并发

关键指标：
- 精确率（Precision）> 90%
- 召回率（Recall）> 90%
- F1-score > 90%
- 误报率（FPR）< 5%

### 第四步：Green-Gate 质量门禁法

**目标：别"差不多就行"，要严格门禁。**

门禁清单：
1. **CI 全绿**——所有步骤通过才能算完成
2. **OpenSSF Scorecard**——目标 10/10 满分
3. **自扫描（dogfooding）**——扫自己，看看有没有问题
4. **误报率达标**——目标 < 5%

### 第五步：LGD 三律验收

**目标：最后验收一遍，确保三律都做到了。**

验收清单：
- [ ] 有籍——CHANGELOG 完整，从 v1 到最新版都有记录
- [ ] 有证——每个结论有测试证据，不是吹的
- [ ] 有门禁——关键节点都过了，不是"差不多就行"

---

## 四、这套方法论能复用吗？

**能！** 不管做什么开源工具，都可以按这套流程来：

| 项目类型 | 适用吗？ |
|----------|---------|
| 安全扫描器 | ✅ 完美适用 |
| 评测器/基准测试 | ✅ 完美适用 |
| CI/CD 工具 | ✅ 完美适用 |
| 纯前端 UI | ⚠️ 部分适用（测试层不一样） |
| 纯数据项目 | ⚠️ 部分适用（门禁标准不一样） |

---

## 五、从 SkillGate 沉淀出来的经验教训

1. **别一开始就追求完美**——先做最小可用版，然后逐步加
2. **误报率是安全工具的生命线**——干净的代码不能误报，有漏洞的代码不能漏报
3. **dogfooding 很重要**——扫自己，看看自己的工具好不好用
4. **CI 全绿是底线**——不要"差不多就行"
5. **每个结论要有证据**——不要说"我们的工具很准"，要说"F1=100%（实跑结果）"

---

## 六、核心判断

LGD-Gate 开源方法论不是凭空想出来的——是从 SkillGate 项目 v1→v7.3 的完整开发过程中，一步一步沉淀出来的。

它的核心就是你的 LGD 三律：**有籍、有证、有门禁**。

把这三律贯穿到开源开发的每一步，就能做出高质量、高可信的开源工具。
