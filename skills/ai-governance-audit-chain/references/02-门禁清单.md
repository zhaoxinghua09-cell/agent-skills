# 门禁清单（L3 Gates）

> 门禁的唯一判据：**动作发生之前，是否有一份人看过的确认记录。**
> 事后追认不算门禁，那叫事后审计。

## 一、按风险等级划分的动作清单

### 🔴 A 级（不可逆 / 直接对外，必须过闸）

| 动作 | 典型场景 | 闸门形式 |
|---|---|---|
| 对外发送 | 发邮件、发消息、发帖、提交表单、提交 PR | 发出前把**全文**展示给人工看，确认后才发 |
| 公开发布 | 上传文件、发布站点、上架内容、对外分享链接 | 敏感扫描 0 命中 + 人工点头 |
| 删除 / 覆盖 | `rm`、`git reset --hard`、覆盖同名文件 | 先出 dry-run 清单（列出将被删/被覆盖的每一项），人工确认 |
| 付款 / 下单 / 签约 | 任何产生资金动作 | 双人确认 |
| 改权限 / 改账号 | 提权、加管理员、改访问范围 | 变更单 + 回滚方案 + 事后复核 |

### 🟡 B 级（可回滚但影响面大，建议过闸）

| 动作 | 闸门形式 |
|---|---|
| 装新依赖 / 升级版本 | 记录版本与来源，说明回滚方式 |
| 批量改文件（>10 个） | 先出改动清单与影响面，人工确认 |
| 改动共享配置（CI、构建、部署） | 变更单 + 生效范围说明 |
| 调用外部付费接口 | 预估用量与成本上限 |

### 🟢 C 级（低风险，留痕即可）

| 动作 | 处理 |
|---|---|
| 读文件、搜索、分析 | 只留 L2 快照，不过闸 |
| 本地新建文件 | 收工时 seal 记录即可 |
| 格式化 / 重排（不改语义） | 留痕 + 说明 |

## 二、闸门的三种实现方式（按投入从低到高）

### 方式 1：人工确认清单（零成本，立刻可用）

动作前把下面这段填完，人不签字就不执行：

```
【高风险动作确认单】
动作：
影响范围：
不可逆部分：
我想做什么：
最坏结果：
回滚方式：
确认人 / 时间：
```

### 方式 2：脚本登记 + 待确认态（本技能提供）

```bash
python scripts/audit_chain.py gate --root . --action "对外发邮件" --detail "收件人A，内容摘要：报价"
# 输出 status=pending，此时 verify 会报 WAIT，出不了"可举证"结论
```

**未确认 = 出不了证。** 这就是闸门的作用：把"要不要放行"这个决定，卡在出证之前。

### 方式 3：系统级拦截（工程化）

在工具调用层拦截：命中 A 级动作清单的请求直接返回"待确认"，不进执行队列。
适合团队化、多 agent 场景；单机小项目用方式 1、2 即可。

## 三、闸门设计的三条纪律

1. **闸门前置，不可后补** —— 门禁写在动作之前；写在之后的，是审计不是门禁。
2. **拒绝要留痕** —— 被拒绝的动作也要记录（谁提的、为什么拒），这是最有价值的治理数据。
3. **不能全设门** —— 门禁过多会导致「无脑点通过」，等于没有门。只对 A 级设硬闸。

## 四、常见误用

| 误用 | 后果 | 正确做法 |
|---|---|---|
| 把"事后补审批"当门禁 | 出事后无法证明当时有人把关 | 确认记录必须早于动作时间戳 |
| 门禁开成"默认通过" | 等于没有闸 | 默认拒绝，显式放行 |
| 所有动作都设门 | 疲劳审批，人开始盲点 | 分 A/B/C 三级，只对 A 级设硬闸 |
| 闸门记录不落盘 | 无法举证 | 写入 `gates.jsonl` |
| 让 AI 自己确认自己 | 自己批自己没有意义 | 确认人必须是独立的另一主体 |
